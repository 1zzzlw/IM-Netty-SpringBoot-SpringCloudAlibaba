### 一、HTTP 握手阶段（建立连接时，仅执行一次）

此时客户端发送的是 HTTP 升级请求，属于**入站事件**，执行顺序：① → ② → ④ → ⑤

1. **① IdleStateHandler**

   先触发（但此时刚连接，还没到 30 秒空闲，暂时无动作），仅作为 “前置监听器” 存在，不影响后续 HTTP 处理。

2. **② HttpServerCodec**（核心 HTTP 编解码）

    - 入站：将底层字节流解码为 `HttpRequest`（HTTP 请求对象，包含升级头信息）。
    - 此时还未涉及出站，编码器暂不工作。

3. **④ HttpObjectAggregator(8192)**（HTTP 消息聚合）

   接收 ② 解码后的 `HttpRequest` 片段，聚合成完整的 `FullHttpRequest`（确保拿到完整的升级请求头），传给下一个处理器。

4. **⑤ WebSocketServerProtocolHandler("/ws")**（握手核心）

   接收 ④ 聚合后的完整 `FullHttpRequest`，验证是否是路径为 `/ws` 的 WebSocket 升级请求（检查
   `Upgrade: websocket` 等头）：

    - 验证通过：返回 HTTP 101 响应（通过 ② 的 HttpResponseEncoder 编码发送，属于出站，此时出站顺序是 ⑤ →
      ②），完成握手，连接升级为 WebSocket。
    - 验证失败：返回错误响应，结束流程。

### 二、WebSocket 通信阶段（握手成功后，持续执行）

此时通信协议切换为 WebSocket，收发数据为帧（`WebSocketFrame`），分 “入站接收” 和 “出站发送” 两种情况：

#### 1. 入站事件（前端发消息到后端）

执行顺序：① → ② → ⑤ → 自定义业务处理器（你后续加的）

- **① IdleStateHandler**

  持续监听：若 30 秒内没收到前端数据，触发 `IdleState.READER_IDLE` 事件（可用于检测客户端断线），事件继续向后传递。

- **② HttpServerCodec**

  此时已升级为 WebSocket，HTTP 解码器不再工作（跳过），仅作为 “通道” 传递字节流给下一个处理器。

- **⑤ WebSocketServerProtocolHandler**（核心帧解析）

  接收字节流，自动解析为 `WebSocketFrame`（文本帧 / 二进制帧），并过滤掉控制帧（如 ping/pong/
  关闭帧，自动处理），只将业务帧（文本 / 二进制）传给后续处理器。

- 最终到你的**自定义业务处理器**，解析 `WebSocketFrame` 中的数据（如文本帧的字符串），处理业务逻辑。

#### 2. 出站事件（后端发消息到前端）

执行顺序：自定义业务处理器 → ⑤ → ③ → ②

- 自定义业务处理器：将业务数据封装成 `WebSocketFrame`（如 `TextWebSocketFrame`），调用
  `ctx.writeAndFlush()` 触发出站。

- **⑤ WebSocketServerProtocolHandler**

  接收 `WebSocketFrame`，确认格式合法后，传递给前一个出站处理器。

- **③ ChunkedWriteHandler**

  若发送的数据是大文件 / 大数据流（如二进制帧内容很大），自动分块发送，避免内存溢出；小数据则直接通过。

- **② HttpServerCodec**（的 HttpResponseEncoder）

  此时已升级为 WebSocket，HTTP 编码器不处理帧，仅将帧的字节流写入底层通道，发送给前端。

- **① IdleStateHandler**：不处理出站事件，直接跳过。

### 总结核心顺序逻辑

- **入站（收数据）**：按添加顺序（①→②→④→⑤→自定义），前四步完成握手 + 帧解析，最终到业务逻辑。
- **出站（发数据）**：按添加逆序（自定义→⑤→③→②），核心是⑤封装帧、③处理大数据、②输出字节流。

每个处理器各司其职，从 “连接握手” 到 “持续通信” 无缝衔接，前面的处理器为后面的铺路，逻辑很连贯。

### 数据不一致性问题

#### 问题场景一：Http请求出现问题
    用户A发送消息给用户B。首先本地存储SQLite存储成功，然后ws实时响应到对方界面，但是异步存储Http请求到后端出现问题，导致前后端数据库的数据不一致，这就需要本地发送消息时，记录消息的发送状态，等待后端的响应，如果后端响应成功，前端的消息状态标识发送成功，否则发送失败进行重试发送，或者是将发送失败的消息不断累积到一个pinia缓存中，只要pinia有发送失败的消息，就不断进行尝试。
#### 问题请求二：启动时进行离线消息同步
    当用户时首次在该设备进行登录时，本地数据库无值或未创建，需要从服务端拉取大量消息进行初始化并进行懒加载动画，但是如果用户有了登陆记录，当退出一段时间后再次登录，本地数据库仍然是旧的数据，所以当打开聊天窗口时，不会看到退出时间段最新的消息和未读消息数量。然后我又听说后端MQ消息队列可以实现离线消息发送，就是暂时存储在消息队列中等待对方上线在进行推送，这个如果理想的话可以进行这个问题的处理思路，但是我觉的不靠谱，MQ消息队列的存储消息数量肯定是有限的，所以我最好的办法就是登录之后再次拉取最新的消息从服务端，但是这样的话是不是就感觉初始化和最新拉取的操作有些重复了。所以我的解决思路是，再次登录，拉取最新消息时，同样需要发送请求给后端来获取最新消息，但是需要携带参数，首先前端查询到sqlite的消息列表时用message进行排序的，即使所有的会话的消息都在一个表内，但是时间肯定是一个标准来区分最新消息和旧的消息吗，我就可以拿到sqlite数据库中目前最新的消息，然后携带在http请求中，此时的查询速度肯定会快不少，后端拿到查询参数，进行查询返回，然后前端写入sqlite数据库。同时记录消息总数，就可以拿到目前未读消息数量的总个数。
#### 问题三：离线时的每个会话的未读消息数量同步
    这个后端的话肯定会更新对方的未读消息数量，但是前端离线的话前端数据库就没办法实时更新了，所以这里也算数据不一致性的问题，首先能想到的解决思路就是再次登录和更新最新消息一样，根据会话的更新时间和创建时间作为参数，发送Http请求更新会话状态。我目前认为这是最靠谱的方法了，会话表的字段很多，所以这次更新可以解决大部分的数据不一致性的问题。

最终解决方案，避免过渡设计，首先知道，实际情况下，我的初始化数据和后续登录初始化数据，他们的短期token全部都是新生成的，根本不存在过期的说法，因此没必要处理刷新token的请求。然后是分块上传，分块上传是一个高并发的请求，每次请求都需要校验，这个对服务端的压力太大了，即使前端限制并发数量，后端使用MQ进行异步处理，我感觉还是不如不进行校验，减轻一点压力，所以我可以添加一个新的请求，就是前端携带长期token发送给后端，先校验，再去发送下面是具体细节

校验什么
/upload/init 时校验：

验证token，确认是哪个用户要上传
生成uploadId并绑定到这个用户
/upload/chunk 时校验：

验证uploadId是否存在（防止伪造）
不校验token（性能考虑）
/upload/merge 时校验：

验证token，确认当前用户身份
验证uploadId是否属于这个用户（防止用户A合并用户B的文件）
验证所有分块是否都上传完成
Redis的作用
临时存储上传任务信息：

uploadId → 用户ID的映射关系
已上传的分块列表
文件元信息（文件名、大小、总分块数）
30分钟自动过期（上传超时自动清理）
为什么不直接用数据库：

上传可能失败/取消，不想在MySQL留垃圾数据
Redis读写快，适合高频的分块上传
自动过期，不需要手动清理
上传成功后：

从Redis读取信息 → 写入MySQL
删除Redis中的临时数据
简单说：Redis是临时工作区，MySQL是最终存档。

Redis的设计和分析思路
    先思考redis的用途：通过缓存解决数据库的频繁访问问题，如果大量用户访问并操作数据库，就会导致数据库的宕机，因此redis出现作为一个缓存解决了这个危险，将可能频繁访问的数据，存入redis中，这样，每次访问都会先访问redis，由于是缓存，查询速度远大于数据库，因此不用担心大量请求的问题，但是这是在设计正确的前提下。redis如果代码不完整，也会有很多缓存的问题。比如缓存击穿，雪崩，缓存穿透等问题，都是redis需要注意克服的缺口。以及缓存和MySQL的数据一致性，这个属于是缓存同步更新策略，其中选择的策略是先更新数据库在删除缓存。缓存之后然后是redis可以生成唯一ID，可以进行分布式锁处理高并发场景，这种通常是对数据库的频繁操作，只是用缓存已经不能得到解决，所以需要使用分布式锁和唯一ID进行优化。然后是redis形成的消息队列，类似MQ可以异步处理的一种轻量实现，缓解了高并发的压力，这基本上就是redis的核心内容

我现在说一下ACK确认收到的机制，就是ws发送消息到对方的话，对方接收到还需要再次发送一次ws的消息到发送者那里，如果没有发送，也就是服务端没有接收到ACK的回应消息，就需要重新发送，这就是ACK的核心思路了

所以需要消息的唯一id。这个消息的唯一id的作用就是，ACK返回时携带他，然后根据id删除redis中的消息缓存，仍然存留的消息缓存就代表对方接收失败，就需要主动重新推送

现在我区分一下消息的已读和未读的两种实现思路的有什么不同。一是一种笨方法，也是我可能写在我项目里的一种方法，就是用户点击一个有未读消息的聊天窗口时，会主动发送一次http请求，携带当前未读消息id，然后清楚未读消息id，以及发送ws消息，通知对方的客户端处理这些未读消息id的状态。达成已读和未读的消息展示，默认时未读，只有被通知到，才会修改状态为已读。这个效率我感觉不是很高。第二种思路就是，使用消息队列了，但是具体的实现思路我还不是特别清楚，但是我直到这个消息队列的实现应该不适应我的项目

我的项目设计的ACK的确认机制是，对方接收到之后再发送一次确认机制给服务端，服务端来判断是否需要重新发送这条消息，但是你说ACK可以感知已读和未读，这个我怎么感觉不出来呢。经过ai的讲解，应该是这样的原因：核心是把「消息送达确认（第一层 ACK）」和「消息已读确认（第二层 ACK）」混在一起了 —— 我之前说的 “ACK 感知已读未读”，不是你设计的 “送达 ACK” 直接管已读，而是「送达 ACK + 已读触发的二次确认」共同构成了 “未读 / 已读” 的完整逻辑
类型	你的 “送达 ACK”	已读确认（二次 ACK）
触发时机	对方客户端收到并解析消息后（比如前端拿到 msg 并展示到聊天列表）	对方用户点击聊天窗口、看到消息后
核心作用	告诉服务端 “消息到客户端了，不用重推了” → 标记 “已送达（未读）”	告诉服务端 “用户真的看到消息了” → 标记 “已读”
对应状态	未读（消息到了，但用户没看）	已读（用户主动查看）
你的项目实现	WS 返回带 msgId 的 ACK → 服务端删 Redis 缓存	HTTP 请求清未读 msgId → 服务端发 WS 通知对方


所以二次确认的http请求发送的这个就是第二层的ACK确认。这个ACK确认其实可有可无，只是一个功能。那么第一次的ACK确认是Netty的通信服务构成的保证消息发送成功，而第二次应用层的ACK确认只是实现了一个功能，豆包给我的总结：
第二层 HTTP 请求 = 第二层 ACK（已读 ACK） ✅：没错，这个请求本质就是「业务层的已读确认 ACK」，它的核心价值是实现 “已读 / 未读” 的业务功能，而非 “消息传输可靠”；
第二层 ACK 确实是 “功能级” 的，可有可无 ✅：哪怕去掉这个逻辑，你的 IM 核心功能（消息可靠收发）依然能用，只是少了 “已读状态展示” 这个体验性功能；
第一层 ACK 是 “可靠性级” 的，是 Netty 通信的核心保障 ✅：没有它，消息就可能丢、可能重复，是支撑 IM “消息能可靠到客户端” 的基础。

1. 第一层 ACK 不是 “Netty 的通信服务自带的”，是你基于 Netty 开发的应用层 ACK
Netty 本身只是一个网络通信框架，它帮你封装了 TCP 的底层，但不会自动帮你做 “消息级的 ACK 确认” —— 你设计的 “对方接收到消息后回 WS ACK、服务端判断是否重发”，是你在 Netty 之上写的「应用层可靠机制」，属于你项目的核心设计，而非 Netty 自带的能力。
简单说：Netty 是 “工具”，第一层 ACK 是你用这个工具打造的 “可靠性保障”。

2. 第二层 ACK 不是 “单纯的功能”，是 “体验级的核心功能”
对 IM 产品来说，“已读 / 未读” 虽然不影响消息传输的可靠性，但却是用户体验的核心 —— 比如微信、QQ 的 “已读 / 未读” 小红点，是用户感知消息是否被查看的关键。所以它不是 “可有可无的鸡肋功能”，而是 “提升产品体验的核心功能”，只是和第一层 ACK 的 “可靠性优先级” 不同。

三、一句话精准总结（面试时直接用）
“我设计的两层 ACK 分工明确：第一层是基于 Netty 实现的「送达 ACK」（WS 返回 msgId 确认），是保障消息可靠传输到客户端的核心，没有它消息可能丢失或重复；第二层是用户点击聊天窗口触发的「已读 ACK」（HTTP 请求），是实现已读 / 未读状态的体验级功能，核心提升用户体验，二者结合既保证了消息可靠性，又满足了 IM 的核心体验需求。”

当服务端没收到第一层 ACK 触发重试时，客户端如何保证消息不重复展示？我的第一次ACK的设计思路是这样的，对方的客户端的ws接收到消息时，此时就说明接收成功了，就会再次发送ACK，但是如果服务端因为网络原因没有收到这个ACK确认消息，就会重复发送这个消息到对方那里从而重复展示，那么这个怎么解决呢

我服务端发送的重复消息，就是当没有收到消息id的时候，会发送redis中未发生的消息，此时就再前端进行唯一校验就可以了

现在考虑一下Netty该怎么判断这个消息什么时候需要重新发送，首先，当我收到客户端发来的ACK确认消息的时候，此时就可以根据这个消息id来删除redis中缓存的消息。但是如果是弱网环境，我的ACK没有即使发送，这是又来了第二条消息，那我怎么保证消息的发送顺序呢。只要是需要展示到对方界面的都是通过ws发送的消息，http发送的消息只是存储到数据库中，那么加入第一条发送失败，没有接收到ACK的确认消息，第二条却发送成功了，此时就直接展示到对方界面了。所以为了保证消息的展示的顺序性，我需要再第一条发送ws消息时没有接收到ACK的话，进行阻塞等待，直到重发接收到ACK，才能redis的队列中取出剩余的消息发送过去，但是很有可能此时已经积累了很多消息了，所以我又需要考虑这种情况怎么解决，肯定时不能一条条的发送，因为同样时需要ACK的确认，这样一条条的阻塞就太慢了。

一、先纠正核心误区：为什么不能 “阻塞等 ACK 再发下一条”？
弱网下一条消息的 ACK 可能延迟 5 秒，阻塞的话后续消息全排队，用户会感觉 “发消息卡死”；
若第一条消息一直收不到 ACK（比如对方断网），后续所有消息都发不出去，体验极差；
Netty 是异步非阻塞框架，强行阻塞会浪费线程资源，违背框架设计原则。

二、正确方案：「异步发送 + 客户端按 msgId 排序 + 批量重推」（兼顾顺序 + 性能 + 可靠性）
这套方案完全适配你的架构，改动极小，核心是「把 “顺序保证” 从服务端转移到客户端」—— 服务端只管异步发消息，客户端收到后按 msgId 排序再展示，彻底解决乱序问题。

步骤 1：给 msgId 增加「递增序号」（核心：保证顺序）
你现有的 msgId 只需要加一个「会话级递增序号」（比如msgId=雪花ID_序号，或单独存序号）

步骤 2：服务端异步发送，不阻塞（核心：保证性能）
服务端逻辑不变，只是新增seq字段，且不管上一条消息是否收到 ACK，都异步发送下一条

步骤 3：客户端缓存消息 + 按 seq 排序展示（核心：解决乱序）
客户端收到消息后，不直接展示，先存入「待排序缓存」，再按seq从小到大取连续的消息展示：

步骤 4：服务端批量重推（优化性能，避免逐条重试）
服务端不用逐条重试，而是「定时批量拉取 Redis 中未收到 ACK 的消息，一次性推送给客户端」：

```
// 定时任务（比如每5秒执行一次）
@Scheduled(fixedRate = 5000)
public void batchRetrySendMsg() {
  // 1. 遍历所有有未读消息的用户
  Set<String> userKeys = redisTemplate.keys("offline:msg:*");
  for (String userKey : userKeys) {
    Long userId = Long.parseLong(userKey.split(":")[2]);
    // 2. 批量获取该用户的未ACK消息（按seq升序）
    Map<Object, Object> msgMap = redisTemplate.opsForHash().entries(userKey);
    List<MsgDTO> msgList = convertToMsgList(msgMap);
    // 3. 按seq升序排序后，批量推送
    msgList.sort((a, b) => a.getSeq() - b.getSeq());
    for (MsgDTO msg : msgList) {
      pushMsgToUserAsync(userId, msg);
    }
  }
}

```

消息id一致性的问题
消息id应该是再后端生成，先说发送消息，发送消息时，我的前端代码就需要直接把这条消息存储到数据库，所以此时的消息id是不能拿到服务端生成的id的。当我发送消息到服务端时，服务端此时可以生成消息id然后存储到消息队列中，并被各个集群所监听，然后发布给对方，此时这条消息就携带着服务端生成的id，对方存储到本地数据库的消息是和服务端生成的消息id是一致的，因此发送方的消息id和接收方的消息id是不可能相同的

因此就需要ACK回执来保证消息id的一致，思路是这样的，发送方的ws发送消息成功后，不会直接把该消息存到本地数据库中，会有专门监听此消息的通道。这里有用户1，用户2，服务器，三个节点。用户1给用户2发送消息，
首先，用户1发送的消息会到达服务器，如果发送成功，服务器会返回接收成功的ACK消息，此时用户1收到这个ACK确认消息之后，在把自己发送的消息存到本地数据库中。如果发送失败，服务端会发送失败的消息，此时不会自动重新发送，而是会改变消息的发送状态未发送失败，就是从转圈加载到感叹号。这就是用户1发送消息经过服务端的这一层通道。
然后服务端的处理，服务端当接收到消息时，需要在服务端生成消息的唯一id，生成之后，再去返回ACK的确认机制，然后把这条发送成功的消息返回给用户1便于他的存储到本地数据库中。然后需要将消息推送到消息队列中，这个消息队列会被所有部署的集群监听，这个就是集群消费的一个队列，然后是还需要把消息推送到Springboot监听的一个消费队列，用来异步存储到数据库中。此时，Netty服务器的工作就完成了。
接着开始说SpringBoot监听到消息队列中有数据该怎么做，就是直接存储到数据库中没什么可以做的
最后就是服务端发送给用户2了，这个也有一个ACK的确认机制，Netty集群从消息队列中监听到消费队列中有数据时，会做一些处理，拿到用户2的channel，然后发送给对方，此时就需要监听用户2客户端返回的ACK确认机制了，如果发送成功，用户2那里直接存储到数据库中然后返回ACK确认，此时Netty服务器收到ACK确认消息后，才会选择把这个消息消费掉，否则就重新发送。
